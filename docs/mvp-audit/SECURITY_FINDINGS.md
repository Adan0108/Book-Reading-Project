# Security findings

Audit target: `main` at `82b4bf9`. All live reproductions used fresh records in isolated `publishing_qa`. No production account or external payment was touched. [EVIDENCE.json](EVIDENCE.json) contains observed statuses without tokens. A reproduction script completing with exit 0 means observations were recorded, **not** that the application passed security review.

## Confirmed release blockers

| ID | Severity / priority | Finding | Evidence and scope | Recommended mitigation |
|---|---|---|---|---|
| S01 | High / P0 | Password setup is not bound to the caller who verified the email | `POST /v1/api/access/setup-password` is public; `services/access.service.ts:setupPassword` checks only email and `state===2`. `SETUP_WITHOUT_PROOF`: a fresh unrelated request with email/password/username and no OTP, cookie or setup token succeeds with **201** for a seeded verified-pending account. | After OTP verification issue expiring, single-use setup proof; require it to complete the account, bind intended user, consume atomically. Test caller substitution and races. This is a pending-setup window takeover, not proof of arbitrary active-account takeover. |
| S02 | High / P0 | Password reset does not revoke existing sessions | Reset writes `TOKEN_IAT_AVAILABLE_<uid>` in `access.service.ts`; neither `checkAuth.ts` nor `optionalAuth.ts` reads it. `RESET_SESSION_REVOCATION`: reset **200**, old access `/user/me` **200**, old RT refresh **200**. | Enforce cutoff/session version on both optional and required auth and refresh, or revoke session families/rotate keys safely. Add real multi-session reset tests. |
| S03 | High / P0 | Refresh-token consumption is not atomic | `requireRefreshToken` checks Redis, then `refreshTokens` separately writes revocation and mints a pair. `CONCURRENT_REFRESH`: two requests with the same RT both **200**; sequential reuse later **401**. Browser single-flight only coordinates one Axios runtime. | Atomically consume a session/RT ID, track family and reuse, issue at most one successor. Test separate clients/tabs, not only sequential requests. |
| S04 | High / P0 | Blocking an account does not invalidate already issued access tokens | Login checks `users.state`, but `authenticationV2` validates only token/key/JTI. `BLOCKED_EXISTING_SESSION`: fresh QA user changed to blocked state 0 still receives `/user/me` **200** using the pre-block token. | Make block/reset events advance enforced session state and revoke refresh as well as access. Test protected and optional routes. |
| S05 | High policy gap / P0 | Book-level restrictions do not constrain otherwise-public chapter content | `book.repo.ts:findBookBySlugPublic` checks publication, not visibility; `book.service.ts:getChapterContent` gates `chapter.visibility` only; `canAccessBookTier` has no caller. `BOOK_VISIBILITY`: `MEMBERS` book with `PUBLIC` chapter returns guest **200**. | Explicitly define inheritance. If book visibility restricts its chapters, enforce the intersection everywhere. If it is metadata only, remove/relabel the misleading author control and document independent chapter policy. Chapter-only member checks passed the tested scenarios. |

## Confirmed code/control gaps and conditional risks

| ID | Severity | Finding and concrete source | Evidence strength / mitigation |
|---|---|---|---|
| S06 | Medium–high | Logout blacklist lifetime follows AT expiry while AT/RT share one JTI and expire after two/seven days (`checkAuth.ts:createTokenPair`, `access.service.ts:logout`) | Immediate logout blocks AT and RT in the probe. Code shows revocation can expire before a copied RT. The multi-day replay was **not** waited out or executed. Revoke for the full session/RT lifetime or separate token types and session families. |
| S07 | Medium | Refresh token is returned in JSON as well as an HttpOnly cookie (`controllers/access.controller.ts:login/refresh` returns `tokens`) | Confirmed serialization; no exfiltration performed. Keep RT solely in its secure cookie, avoid exposing it to browser scripts and logs. AT is stored in localStorage by `useAuthStore.ts`; XSS impact is therefore material even though tested Markdown payloads were blocked. |
| S08 | Medium | Incomplete browser logout cleanup (`frontend/src/store/useAuthStore.ts`) | Successful normal logout clears userId and memory but not localStorage accessToken; an early no-authUser path clears locally without contacting backend. Code-confirmed, not a complete browser session replay test. Consolidate cleanup and verify server revocation before claiming global logout. |
| S09 | Medium | No general login/IP throttling or global email-abuse limit in routes/services | OTP has per-user one-minute resend cooldown, ten-attempt invalidation and Redis counters; upload intents have quotas. These are not platform-wide login/register protection. Add bounded server-side controls. No brute-force load test was performed. |
| S10 | Medium | Approval is nontransactional and does not provision `authors` (`application.service.ts:approve`) | `AUTHOR_APPROVAL`: approval 200, author profiles 0, publishing 403. Role is granted before decision update; races/partial failure can leave inconsistent state. Provision profile/role/decision atomically and idempotently; UI cannot repair this backend invariant. |
| S11 | Medium | Legacy upload bypasses new quotas; deletion precedes DB removal (`routes/upload/index.ts`, `services/upload.service.ts:removeFanArtService`) | Authenticated legacy route buffers up to 5 MB with MIME filtering and streams to cloud without new intent quotas. Deletion derives public ID from URL, destroys cloud resource, then deletes row. Static finding; no upload/deletion attempted. Align rate limits and use authoritative identifiers/reference reconciliation before deprecation. |
| S12 | Medium | Cached hidden-book metadata can remain visible after out-of-band status changes | `HIDDEN_BOOK_CACHE`: warmed detail 200 after direct QA SQL hide, chapter content **404**. Normal publishing service invalidates the book cache; no admin hide API exists yet. This is **not** proof of a current admin endpoint bypass or paid-text cache leakage. Implement moderation with explicit invalidation and fresh availability checks; do not rely on raw SQL updates/TTL. |
| S13 | Medium conditional | SMTP certificate validation can be disabled with `EMAIL_ALLOW_SELF_SIGNED=true` (`utils/sendMail.ts`, `.env.example`) | Code/config option confirmed; production deployment value is UNVERIFIED. Require certificate verification in production, fail closed on unsafe settings and use a test SMTP sink for development. SMTP was disabled for probes. |
| S14 | Medium availability / P1 | Bad pagination yields server errors; large text has an implicit limit | `DISCOVERY`: `/books?page=not-a-number` returns **500**; `LONG_TEXT_LIMIT`: 112,640 content bytes returns **413**. `book.service.ts` coerces page/limit without finite integer validation; `app.ts` uses default JSON limit. Validate inputs and publish explicit byte limits while preserving local text on errors. |
| S15 | Medium operations | Startup/migration safety and credential examples need hardening | `app.ts` begins datastore initialization asynchronously and `server.ts` immediately listens; failures are logged but readiness not gated. `dbs/migrate.ts` lacks lock/checksum and uses transactional wrappers around schema DDL. Compose exposes DB/Redis ports and fixed development passwords; `docker:down` uses `-v`. No normal DB migration or destructive command was run. Add readiness, migration orchestration, production secret provisioning and backups. |
| S16 | Low–medium privacy | Decoded auth payloads and user/profile context are logged (`controllers/book.controller.ts`, `requireRoles.ts`, `useAuthStore.ts`) | Source-confirmed logging of uid/email/JTI/claims and profile data, not evidence of raw secret-key logging. Redact unnecessary request/user context and avoid logging Axios error configurations containing Authorization. |
| S17 | Product requirement gap | Actual JWT algorithm is **HS256**, despite public/private key names | `JWT_ALGORITHM` confirms this is symmetric signing with different random strings. It fails the task's explicit asymmetric-signing requirement, but HS256 by itself is **not** classified as a proven cryptographic exploit. Implement explicit approved asymmetric keys/algorithms if that requirement remains binding. |

## Paid-media and membership caveats

`publishing_assets.image_url` uses Cloudinary `type=upload` delivery. API authorization protects asset attachment and chapter metadata retrieval, not a media URL already known to a user. The audit made no cloud requests to test delivery. If supporting illustrations must be confidential, define a protected-delivery policy and test it; do not assume API locks alone protect public CDN URLs.

`membership.repo.ts:getActiveMembership` checks user, author, ACTIVE status and end time. It does not join tier `is_active` or enforce a future `started_at`. Whether cancellation grace, paused tiers and future starts should revoke/grant access must be explicit before payment events begin creating entitlements. These cases were identified from code, not exercised as paid transactions.

No provider webhook exists, so webhook forgery/duplicate payment grants cannot currently be tested. Their absence is a missing business/security module, not evidence that implemented payment processing is safe. No client-controlled membership activation endpoint was found.

## Checks that passed and boundaries on conclusions

- Guests received 401; logged-in nonmembers, other-author members, expired/cancelled memberships and a disallowed tier received 403. An active permitted tier received 200. A warmed member cache did not grant guest access. Switching a warmed public chapter to MEMBERS through the publishing API changed guest access to 401.
- Immediate logout denied the old AT and old RT with 401. Sequential refresh replay was denied after the successful rotation.
- Existing tests rejected cross-author assets, wrong URL book/chapter scope, forged asset IDs and arbitrary cover attachment. Database rollback/order/idempotency tests passed. No current-audit live cloud verification was attempted.
- Markdown rendered semantic headings/emphasis, inserted no executable content script in the tested payload and stripped tested `javascript:` link navigation. This is one rendering boundary check, not proof of universal XSS immunity or safe arbitrary HTML.
- Core repository SQL values use placeholders; no confirmed SQL injection was found. Invalid pagination is an input-validation/availability defect, not demonstrated SQL injection.
- Refresh cookies are HttpOnly, SameSite=Lax, and Secure in production by code. CORS restricts the configured frontend origin; bearer/custom client-ID headers limit simple cross-origin form attacks. No cross-site refresh/CSRF bypass was demonstrated. Full deployment-origin/cookie testing remains UNVERIFIED.
- Admin application list allowed admin 200 and denied reader 403. This does not make the absent moderation dashboard complete.
